# zatu — 言語設計・開発コンテキスト

## 0. この文書の目的

この文書は、実験的プログラミング言語「zatu」の設計思想、検討中の仕様、開発方針を、別のAIエージェントへ引き継ぐためのものです。

記述には、開発者が明確に希望した方針と、議論中のアイデアが混在しています。

**確定していない構文や機能を、勝手に最終仕様として扱わないでください。**

最初から大規模な実装を目指すのではなく、設計思想を守りながら小さく実験することを重視します。

---

# 1. 概要

**名前：zatu**

**キャッチコピー：雑に書けば、動く。**

**目標：7歳でも、難しい概念を覚えずに、思いついたプログラムを書いて動かせる言語。**

zatuは、プログラミングに必要な「考える量」と「覚える量」を極限まで減らすことを目指す。

短いコードを書くことが目的ではない。

**人間が考えなくてもいいことを、コンピュータに考えさせる。**

これがzatuの中心的な哲学である。

プログラミングの初心者が挫折するのは、単に構文を知らないからではない。

例えば、次のようなことが負担になる。

- 何の機能やライブラリを使えばいいのか分からない。
- 同じことを実現する書き方が複数あって迷う。
- 二重ループやインデックスの操作が難しい。
- どのタイミングでエラー処理を書くべきか分からない。
- クラス、インターフェース、ポインタなどを理解する必要がある。
- 記号や特殊な構文を大量に覚えなければならない。
- 正しく設計してからでないと書き始められない。

zatuは、これらをできる限り言語と開発ツールの側で解決する。

一方で、初心者しか使えない教育用言語にはしたくない。

**簡単な考え方の延長で、本格的なアプリケーションも開発できる言語**を長期的な目標とする。

# 2. 最重要の設計原則

## 2.1. 考える量を減らす

zatuで最も重要なのは、記述量の削減ではなく、認知負荷の削減である。

例えば、型推論を使って型宣言を省略するだけでは不十分。

それ以前に「この場面ではどの型を選ぶべきか」という判断自体を減らしたい。

目指すのは次のような設計。

- 自動で判断できることは自動化する。
- 人間に不要な選択肢を提示しない。
- 同じことをするための方法を無闇に増やさない。
- 特別な概念を知らなくても、自然なコードで目的を達成できる。
- 単純なコードを書くために、高度な概念の理解を要求しない。

**省略できる文字ではなく、不要にできる思考を探す。**

## 2.2. 道具選びで迷わせない

これは特に重要な設計課題。

プログラミングでは、問題を解く前に「何を使うか」を選ぶ必要がある。

例えば、配列を処理する場合でも、for、map、filter、reduce、iterator、その他のAPIなど、多数の選択肢が存在する。

zatuでは、まず素直なfor文で書けばよい。

```zatu
adults := []

for user in users {
    if user.age >= 18 {
        adults += user
    }
}
```

これが普通に書けて、分かりやすく、十分な性能で動くことを目指す。

ただし、高階関数を禁止することが目的ではない。

**難しい道具を知らなくても、普通の方法で困らないこと**を重視する。

## 2.3. ループとインデックスの複雑さを減らす

特に初心者が困るのは次の問題。

- 二重ループ
- インデックスのずれ
- 0始まりと1始まり
- 配列の範囲外アクセス
- どちらのループが先に実行されるか
- 二次元配列の行と列
- 複数配列の組み合わせ処理

例えば、通常のループは次のように書きたい。

```zatu
for item in items {
    print(item)
}
```

インデックスが必要なら、次の構文を検討する。

```zatu
for item at i in items {
    print(i, item)
}
```

さらに、二次元配列について次のような構文案がある。

```zatu
for cell at y, x in board {
    print(cell)
}
```

行と列の数を取得したり、二重ループを書いたりしなくても全要素を走査できる。

ただし、以下は異なる操作なので、意味を混同しない。

1. 二次元配列の全要素を走査する。
2. 2つの配列の同じ位置の要素を扱う。
3. 2つの配列の全組み合わせを扱う。

これらを少ない規則で、直感的かつ曖昧さなく表現できないか検討する。

`at y, x` 案には次の問題があり、未解決。

- `y, x` と `x, y` のどちらの順か、という**並び順そのものが「行と列の混乱」の原因になる**。順番を覚えさせない表現が必要。
- 行ごとに長さが違う配列（ジャグ配列）をどう扱うか。

ループの可視化や、実行中の値をエディタに表示する機能も構想している。

## 2.4. 動作は予測可能にする

「雑に書ける」は「雑に動く」という意味ではない。

例えば、曖昧な記述をコンパイラが勝手に解釈し、予想外の処理をするのは望ましくない。

原則として、

**ひとつの書き方には、予測できる一貫した意味を持たせる。**

自動化する場合でも、動作の透明性は保つ。

### 「雑に書ける」の意味（決定）

「雑に書ける」とは、次のことを指す。

- 書きやすい。
- メソッドや道具の違いを意識せずに書ける。
- 覚えることが少ない。

**エラーを含むプログラムは実行しない。** 型の不一致や未処理のエラーがあれば、実行前にコンパイラが止めて、何が問題でどう直すかを教える。

「エラーがあっても動く部分だけ動かす」方式は採らない。

## 2.5. 覚える概念を減らす

次のような概念を、最初から理解しなくてもプログラミングできるようにしたい。

- クラスとインターフェース
- ポインタと参照
- メモリ管理
- 所有権とライフタイム
- 高階関数
- Effect System
- HandlerとCapability
- 複雑な例外処理

ただし、内部実装までこれらを禁止するわけではない。

**言語内部が複雑でも、ユーザーに見える世界は単純でよい。**

## 2.6. 作りながら学べる

最初にすべての文法や設計概念を勉強する必要はない。

変数、if、for、関数だけを知っていれば、かなりのことができるようにしたい。

分からないことがあれば、その場でエディタやコンパイラが教えてくれる。

# 3. Goから受け継ぎたい特徴

開発者はGoを好んでいる。

特に好きな部分は次のとおり。

- 構文が比較的単純である。
- for文で愚直に処理できる。
- 静的型付けがある。
- 型推論が使える。
- 関数が分かりやすい。
- エラーを明示的に扱う思想。
- ポインタレシーバーによって元の値を直接変更できる便利さ。
- 標準ツールが統一されている。

一方、次の部分には不満がある。

- `if err != nil` を繰り返し書く。
- 初心者がエラー処理を忘れる。
- ポインタの理解が難しい。
- クラスやインターフェースの概念は学んでも分かりにくい。
- `&` や `%d` などの記号を覚える必要がある。
- `append()` と `+=` など、操作ごとに書き方を覚える必要がある。
- 単純な処理でも道具や実装方法を選ばなければならない。

zatuは、Goのシンプルさを残しながら、これらの認知負荷を減らす。

単なるGoの短縮版にはしない。

# 4. 基本言語仕様の案

以下は設計例であり、構文は未確定。

## 4.1. 変数

```zatu
name := "ようかん"
age := 7

age += 1

print(name)
print(age)
```

- `:=` による定義を採用する方向。
- 静的型付けと型推論を重視する。
- 必要な場合は明示的な型指定もできる。
- 再代入とイミュータビリティの詳細は未決定。

不変性の考え方自体は比較的理解しやすいため、関数型の利点も活用したい。

### 検討中：`=` への統一

定義（`:=`）と再代入（`=`）を書き分けること自体が覚える負担になるため、できるなら `=` に統一したい。

`=` に統一したときの問題と対策：

| 問題 | 対策案 |
|---|---|
| 書き込み側のタイプミス（`coutn = count + 1`）で新しい変数ができてしまう | 「代入したのに一度も使われていない変数」をエラーにする |
| 定義前の読み出し（`total = total + 1`） | 「値が決まっていない変数を読んだ」エラーにする |
| `if` の中で作った変数が外で使えない | 変数の有効範囲を関数単位にし、すべての分岐で値が決まっているかを検査する |
| 外側と同じ名前の変数を内側で作る（シャドーイング） | シャドーイングを禁止する。同じ名前は常に同じ変数 |
| 途中で別の型の値を入れる（`x = 1` の後に `x = "a"`） | 型エラーにする |

`:=` の方が良いのは、「ここで新しく作った」が読む人に見える点。ただし、これはエディタで最初の代入を強調表示すれば補える。

## 4.2. ユーザー定義型

```zatu
type User {
    name string
    age int
}

user := User("ようかん", 7)

print(user.name)
```

型は明示的に定義できるようにしたい。

ただし、クラス、継承、インターフェースを最初から必須の概念にはしない。

基本的には、データの形を定義するものとして理解できることが望ましい。

## 4.3. 関数

```zatu
add(a int, b int) int {
    return a + b
}

print(add(1, 2))
```

Goのような素直な構文を好む。

`func` や `fn` を付けるかは未決定。

関数を高度な抽象概念としてではなく、「入力を受け取り、処理して、結果を返すもの」として自然に扱いたい。

キーワードの有無よりも、**関数を書くこと自体をもっと簡単にしたい。** 検討中の案：

- `main` 関数を必要としない。ファイルの上から順に実行される。
- 関数は定義の前でも呼び出せる（定義順を気にしなくてよい）。
- 引数の型を省略できる。型は呼び出し方から推論する。
- キーワード（`func` など）を付けると、「関数の定義」と「関数の呼び出しの後にブロック」との構文上の曖昧さがなくなる。

## 4.4. メソッド

オブジェクト指向っぽく次のように書けることは魅力的。

```zatu
user.greet()
```

一方、メソッドと関数を別々の概念として学ぶ負担は減らしたい。

そこで、以下を同じ実体の呼び出し構文として扱う案がある。

```zatu
greet(user)
user.greet()
```

ただし、名前解決、関数の衝突、可変性については設計が必要。

クラスベースのオブジェクト指向をそのまま再現することは目的ではない。

## 4.5. 配列

```zatu
numbers := [1, 2, 3]
numbers += 4
```

`append()` などの個別APIを大量に覚えさせず、直感的な操作を実現したい。

ただし、以下のようなコードの意味が曖昧になる問題がある。

```zatu
numbers += [5, 6]
```

要素の追加、配列の連結、ネストした配列の追加は区別する必要がある。

無理にすべてを `+=` に統一しない。

## 4.6. 値の独立性

重要な基本方針として、**普通のデータを代入すると、論理的には独立した値になる**方向を希望している。

```zatu
a := User("ようかん", 7)
b := a

b.age = 8

print(a.age) // 7
print(b.age) // 8
```

元の値が知らないうちに変化しないことを重視する。

ただし、実際に毎回メモリを丸ごとコピーする必要はない。

Copy-on-Write、所有権解析、参照カウントなどによって内部で最適化することは可能。

### 未解決：元の値を直接変更する操作

Goのポインタレシーバーのような、元の値を直接変更する操作にも魅力を感じている。

```zatu
birthday(mut user User) {
    user.age += 1
}
```

これは構文案。

ただし、呼び出し元の値を変更する関数は、通常の純粋関数とは異なる。

純粋な値の独立性を守りながら、必要なときだけ直接変更する仕組みを検討する。

ポインタの記号を見せずに実現できることが望ましい。

`mut` 以外の案：

1. **新しい値を返して代入し直す**：`user = birthday(user)`。新しい概念はゼロ。代入し忘れは「戻り値を捨てている」エラーで検出する。
2. **変更を推論する**：関数が引数を書き換えていれば、呼び出し元の値も変わる関数として扱う。書く量は最小だが、関数の中身を変えると呼び出し元の動作が黙って変わるため、§2.4 と衝突しやすい。
3. **メソッド呼び出しの形だけ変更を許す**：`user.birthday()` なら `user` が変わる、`birthday(user)` なら変わらない。見た目で区別できるが、§4.4 の「関数とメソッドを同じものとして扱う」案と衝突する。

### 未解決：ループ変数の変更

```zatu
for user in users {
    user.age += 1   // users は変わる？
}
```

黙って何も起きない（Goのrange変数と同じ挙動）のは避ける。変更できないようにしてエラーで教えるか、要素そのものを変更できるようにするかを決める必要がある。

## 4.7. 文字列（決定）

文字列の長さとインデックスは**文字数（見た目の1文字）単位**とする。

```zatu
name := "ようかん"
print(len(name)) // 4（バイト数の 12 ではない）
```

内部表現（UTF-8など）は利用者に見せない。

# 5. エラー処理の思想

開発者はGoの明示的なエラー処理自体を嫌っているわけではない。

問題は、初心者が「いつエラー処理を書く必要があるか」を知らないこと。

例えば、

```zatu
data := file.read("hello.txt")
print(data)
```

というコードを書いたとする。

ファイル読み込みは失敗する可能性がある。

zatuでは、コンパイラが未処理のエラーを検出し、エディタが対処方法を提案することを目指す。

候補は、

- エラーを呼び出し元に伝える。
- エラーをその場で処理する。
- 失敗した場合の代替値を使う。

など。

自動伝播を表す `?` や、代替値を表す `or` などの構文も考えられるが、未決定。

**エラーを勝手に無視したり、成功したことにしたりしてはいけない。**

# 6. 副作用・DI・関数型の考え方

zatuでは、関数型プログラミングの利点も取り込みたい。

特に、

- 予測しやすい処理
- 純粋関数
- 意図しない共有状態の削減
- テストのしやすさ
- 副作用の把握

を重視する。

ただし、純粋関数型言語を目指すとは限らない。

ローカル変数を変更しながら、外部には副作用を出さない処理も自然に書けるようにしたい。

## 6.1. 副作用の自動推論

コンパイラが関数の呼び出し関係を調べ、ファイル、ネットワーク、DBなどの副作用を追跡する案。

```zatu
save(user User) {
    database.write(user)
}
```

ここで `database.write()` が副作用を持つことをコンパイラが把握し、`save` のEffectを推論する。

利用者が毎回Effectを宣言する必要はない。

エディタがGoのimport自動補完のように、必要な宣言を提示できるとよい。

純粋性を保証したい場合だけ明示的に指定する仕組みも考えられる。

## 6.2. DI

関数やメソッドが依存する外部機能を、実装と分離してテストしやすくしたい。

ただし、Effect、Handler、Capabilityなどの複数の概念を、初心者が最初から理解する必要がない設計を目指す。

DI自体を意識せずに使える方法も検討したい。

**注意：DIとEffect追跡は別問題である。**

DIで依存を注入できても、副作用がなくなるわけではない。

## 6.3. 優先順位

副作用推論やDIは重要だが、現時点でzatuの最優先課題ではない。

最も大事なのは、

**「何を使えばいいか」「どう書けばいいか」という判断の負担を減らすこと。**

高度なEffect Systemを最初から実装する必要はない。

# 7. 革新的な機能の構想

## 7.1. 未完成でも理解できるプログラム

書きかけのコードであっても、意味が確定している部分を解析できる仕組み。

例えば、

```zatu
numbers := [1, 2, 3]

for n in numbers {
    print(n * )
}
```

右辺が未完成でも、そこに数値が必要であることや、その時点までの変数の値を表示できないか。

Typed HolesやLive Programmingの研究を参考にできる。

これはエディタ上の解析・表示の話であり、実行の話ではない。§2.4 のとおり、エラーを含むプログラムは実行しない。

特にファイル操作、ネットワーク操作などの副作用は慎重に扱う。

## 7.2. ループの可視化

二重ループやインデックスの変化を、エディタが視覚的に説明する。

例えば、

```zatu
for item at i in items {
    print(item)
}
```

について、現在の `i` と `item`、処理済みの要素をリアルタイムで確認できるようにする。

ループの実行順序を頭の中でシミュレーションする必要を減らす。

## 7.3. 素直なコードを効率よく実行する

初心者が単純なfor文で書いた処理を、処理系が可能な範囲で最適化する。

ただし、すべての非効率なアルゴリズムを自動で高速化できるわけではない。

「複雑な書き方を知っている人だけが性能を得られる」という状況を、できる限り避ける。

## 7.4. 例から処理を考える

例えば、

```zatu
double(2) == 4
double(3) == 6
double(10) == 20
```

という入出力例から、実装を提案できないか。

Programming by Exampleに近い方向。

ただし、これを初期段階で実装する必要はない。

AIや自動生成がなくても、言語単体で使いやすいことを重視する。

# 8. 技術的な実装方針

## 8.1. Rustで実装する

初期実装はRustを予定している。

最初からLLVM、WASMコンパイラ、JITなどを作る必要はない。

まずは小さなASTインタプリタを実装する。

```text
zatu/
├── Cargo.toml
├── mise.toml        # Rust のバージョン（mise で管理）
├── src/
│   ├── main.rs      # コマンド（zatu ファイル.zt）
│   ├── lib.rs       # 解析 → 検査 → 実行 をつなぐ
│   ├── lexer.rs     # 字句解析
│   ├── parser.rs    # 構文解析（手書きの再帰下降）
│   ├── ast.rs       # 構文木
│   ├── check.rs     # 実行前の検査
│   ├── eval.rs      # 構文木をたどって実行するインタプリタ
│   ├── value.rs     # 実行時の値（Copy-on-Write）
│   └── error.rs     # エラーの表示
├── examples/        # サンプル（*.zt）
├── tests/lang.rs    # 実際の zatu コードを動かすテスト
└── docs/
    └── 言語設計.md
```

必要に応じて型チェッカーなどを追加する。

LexerとParserは手書きから始めてもよい。Chumskyなどを使うことも検討できる。

v0 は手書きで実装した。§7.1（未完成のコードの解析）にはエラーから回復できるパーサが、§7.2（ループの可視化）には実行過程を記録できる評価器が必要になるため、どちらも後から足しやすい形を保つ。

## 8.1.1. v0 の仮決定

v0 は「作って、書いて、使ってみる」ための実装。以下は**すべて仮決定**で、使ってみて変える前提とする。

| 項目 | v0 での仮決定 |
|---|---|
| 変数 | `=` に統一。`:=` を書くと「= だけで作れます」と案内する |
| 変数の有効範囲 | 関数単位。シャドーイングなし。関数の中から関数の外の変数は見えない |
| タイプミス対策 | 「値を入れたのに使っていない変数」「作られていない変数を読んでいる」を実行前のエラーにし、似た名前を候補として出す |
| エラー時の動作 | 実行前の検査でエラーがあれば1行も実行しない。型検査はまだないので、型の不一致は実行時エラー |
| 値の種類 | 一度入れた値と別の種類の値は入れられない（`x = 1` の後に `x = "a"` はエラー） |
| 数 | 64bit 整数のみ。割り切れない割り算とオーバーフローはエラー（勝手に切り捨てない） |
| 文字列 | 長さと `[i]` は見た目の1文字単位。`"{式}"` で値を埋め込める |
| インデックス | **1 始まり**。`[0]` は「1 から始まります」と案内する |
| 範囲 | `1..10` は 1 から 10 まで（両端を含む） |
| ループ | `for x in xs`、`for x at i in xs`、`for 条件 { }`、`for { }`、`break`、`continue` |
| ループ変数 | 変更できない（エラーで `xs[i]` を使う方法を案内する） |
| ループ中の配列の変更 | くり返す回数は、ループ開始時点の配列で決まる |
| 配列 | 中身は同じ種類の値にそろえる。`+=` は要素1つの追加のみ。配列どうしの連結は未提供 |
| 関数 | `func 名前(引数) { }`。引数と結果の型は省略できる。定義の前でも呼べる。`main` 不要 |
| 元の値を変える操作 | `mut` なし。`user = birthday(user)` のように結果を入れ直す。結果を捨てるとエラー |
| メソッド | `x.f(y)` は `f(x, y)` と同じ（UFCS） |
| ユーザー定義型 | `type User { name string  age int }`、`User("ようかん", 7)`（順番で渡す） |
| 論理演算 | `and` `or` `not`（`&&` `||` `!` は案内付きのエラー） |
| 組み込み関数 | `print` `len` `input` `random(a, b)` `int` |
| 識別子 | 日本語も使える。全角スペースは空白として扱い、全角の記号は半角を案内する |

## 8.2. 最初に実装する機能

初期段階では以下を優先する。

1. 整数と文字列
2. 四則演算
3. 変数の定義と代入
4. `print`
5. `if`
6. `for`
7. 配列
8. 関数
9. ユーザー定義型

型検査や副作用推論などは段階的に追加する。

型システムを後から導入しやすいようにASTを設計することは望ましいが、過剰な将来対応で初期開発を重くしない。

## 8.3. WASM

将来的にzatuのコードをWebAssemblyにコンパイルする案がある。

WASMをターゲットにすれば、ブラウザ上のPlaygroundやWasmtimeでの実行が可能になる。

しかし、初期段階では優先しない。

## 8.4. メモリ管理

利用者に手動のメモリ管理を要求しない。

GC、ARC、Copy-on-Write、Ownership解析などは内部実装の候補。

値の独立性という言語仕様を優先し、その実現方式は後から検討する。

GCを使わないこと自体を目標にはしない。

# 9. 他言語との関係

## Go

もっとも大きく影響を受けている言語。

構文の素直さ、型、関数、for文、明示的なエラー処理などを参考にする。

ただし、Goで必要になる記述や判断をさらに減らしたい。

## Ruby・Python

気軽に書き始められることを参考にする。

一方、動的型付けや豊富なメソッドをそのまま採用するとは限らない。

書きやすさだけでなく、覚えるAPIの量も重視する。

## Rust

主に処理系の実装言語として利用する。

Rustの所有権やライフタイムを、zatu利用者にそのまま要求するつもりはない。

## Emela

Effect System、Handler、Capability、メモリ管理などの設計が参考になる。

しかし、zatuは高度な言語理論を利用者に理解してもらうことを目指さない。

「Emelaの簡易版」を作るのではなく、より少ない概念で直感的にプログラムを書ける方向を探る。

# 10. 現在の設計状況

## 方針として強く合意しているもの

- 名前は `zatu`。
- 7歳でも書けるほど簡単な言語を目指す。
- 考える量と覚える量の削減が最優先。
- Goの素直な構文を参考にする。
- 型を定義できる静的型付けを目指す。
- 型推論を重視する。
- 普通のfor文を大切にする。
- ループとインデックスの難しさを減らす。
- 道具選びに迷わせない。
- 普通のデータの代入では独立した値として扱う。
- メモリ管理を利用者に押し付けない。
- エラー処理を忘れた場合に教える仕組みを目指す。
- 副作用の自動追跡に関心がある。
- Rustで小さく作り始める。
- エラーを含むプログラムは実行しない（「雑に書ける」は書きやすさと覚える量の少なさを指す）。
- 文字列の長さとインデックスは文字数単位。
- 気軽に開発し、実験しながら設計を変えていく。

## 未決定の重要事項

- `:=` と `=` を `=` に統一するか
- 変数のデフォルトの可変性
- ループ変数を変更したときの挙動
- 関数定義の簡略化（キーワード、引数の型の省略、`main` 不要）
- 純粋性と破壊的変更の扱い
- `mut` のような構文を導入するか（代替案は §4.6）
- 関数とメソッドの関係
- 型の共通化・多態性の表現
- `+=` による配列操作の意味
- 二次元配列や複数配列の反復構文（行と列の順番、ジャグ配列）
- インデックスの仕様
- エラーの伝播構文
- エラーを型システムでどう表現するか
- Effect Systemの具体的な設計
- DI・Capabilityの扱い
- GCやARCなどのメモリ管理方式
- WASMへのコンパイル方式

未決定事項を一度に決める必要はない。

# 11. 開発・ドキュメント方針

個人の実験的プロジェクトとして、気軽に開発する。

最初からOSSプロジェクトとして完璧に整備する必要はない。

言語は次のように使い分ける。

- README：まず日本語
- 設計ドキュメント：日本語
- コードの識別子：英語
- Rustのコメント：日本語でもよい
- コミットメッセージ：英語を基本とする
- 将来的にREADMEやドキュメントの英語版も作る

言語設計上の重要な判断は、簡単な理由を残しておくとよい。

# 12. 今後の設計判断の基準

新しい機能を追加する際は、次のことを検討する。

1. これによって考える量は減るか？
2. 覚えることが増えないか？
3. 別の機能を覚えずに実現できないか？
4. 既存の構文や概念を再利用できないか？
5. 何も知らない初心者が動作を予想できるか？
6. 自動化によって危険な動作や曖昧さが生まれないか？
7. 普通のコードを普通に書くだけで済むか？

新しい機能を追加したことで、別の選択肢が増えてしまう場合は慎重に考える。

**機能の多さより、判断の少なさを優先する。**

# 13. 他のAIエージェントへの指示

このプロジェクトを支援する際は、次のことを意識してください。

- 言語仕様を必要以上に複雑にしない。
- Rustの慣習をそのままzatuに持ち込まない。
- Goに似ていることを目的にしない。
- 関数型やオブジェクト指向を無理に押し付けない。
- 実装の美しさより、利用者の理解しやすさを重視する。
- 新しい概念を追加する場合は、その必要性を説明する。
- 複数の設計案がある場合は、記述量ではなく認知負荷で比較する。
- 型の安全性と直感的な動作を両立できるか検討する。
- 仕様として決まったものと、単なる提案を区別する。
- 初期実装はできる限り小さくする。
- 難しい技術を採用すること自体を成果としない。
- 必要に応じて、実際の初心者に試してもらう方法も提案する。

特に重要なのは、**「初心者が何に迷っているのか」を出発点にすること**です。

例えば「二重ループが難しい」という問題に対して、単に二重ループを短く書く構文を追加しても、本質的に解決したとは限りません。

そもそも二重ループとして考える必要がない方法を探してください。

# 14. 最終的なビジョン

zatuは、難しい概念を学ぶこと自体を目的としない。

プログラミングは、本来やりたいことを実現するための道具。

その道具の使い方を覚えるだけで疲れてしまうのでは、本末転倒である。

zatuでは、思いついた処理を素直に書けば、それが可能な限り予測どおりに動く。

必要なときには、コンパイラやエディタが足りない情報を教えてくれる。

プログラミングの知識が増えても、同じ単純な考え方を使い続けられる。

そして、zatuそのものの開発も気軽に楽しむ。

最初から完璧な言語を作る必要はない。

実際に書いて、動かして、不便だと思ったことを少しずつ減らしていく。

**zatu — 雑に書けば、動く。**

*人間はやりたいことを考える。面倒なことはコンピュータが考える。*
